## 1. 游戏概况与镜像结构

Deep Freeze 是 Microcabin 1996 年在 PS1 上发行的救援动作游戏：玩家扮演
SWAT 队长，进入被恐怖分子占领的摩天大楼解救人质。全部文本集中在
菜单/简报 (MENU1-5)、剧情对话 (OVERLAY) 与任务教学模式 (SCRIPT.B)。

镜像为标准 PS1 压制盘：

| 项目 | 值 |
|------|-----|
| 轨道 | TRACK 01 MODE2/2352 + 6 条音轨 |
| 扇区 | 2352 B/扇区, 用户数据 2048 B @ +24 |
| 大小 | 495,531,120 字节 |
| EXE  | `SLPS_018.17`, LBN **24**, 417,792 B (0x800 头 + 0x65800) |
| 装载 | 运行时基址 `0x80010000`, 镜像内 EXE 头声明的跳转入口正常 |

EXE 定位：逐扇区在 +24 偏移搜索 `PS-X EXE` 魔数即可 (LBN 24)。

全部资源打包在 18 个 `.SAF` 文件中 (自定义容器)，镜像中的位置见
`data/original/saf_lbn.json`。含文本的 SAF：

| SAF | LBN | 大小 | 内容 |
|-----|-----|------|------|
| OVERLAY.SAF | 25519 | 247,808 | 关卡脚本+对话+教学模式 (34 个 .B) |
| MENU1-5.SAF | 26554/26780/26944/27137/27288 | 280-462 KB | 各关卡菜单/简报/武器说明 |
| SYSTEM.SAF  | 27425 | 505,856 | **字库/码表** + 系统界面资源 |

> 重要教训：从 2352 原始镜像读取数据时**必须逐扇区取 +24 用户数据**。
> 把整盘当连续文件流 `read(2048)` 会读到扇区头垃圾，解压出乱码——
> 本项目早期曾因此误判 STAGE05B.B "损坏"，实际毫无问题。

## 2. SAF 资源包格式

SAF ("SOF" 魔数，源自 Microcabin 自家格式) 是极简的资源容器：

```
偏移  类型          含义
0x00  u32 LE       条目数 N
0x04  20B × N      目录项
...                数据区 (按目录项扇区号索引, 单位 2048B)
```

每个目录项 20 字节：

```
[0..10]  文件名, NUL 终止 (最多 8.3; 可能带 '*' 前缀)
[11]     解压大小 bits 16-23
[12..13] u16 LE 数据起始扇区 (相对 SAF 头)
[14..15] u16 LE 解压大小 bits 0-15
[16..17] u16 LE 压缩数据长度 clen
[18]     保留
[19]     解压大小 bits 8-15 重复位 (见下)
```

**游戏的解压大小计算是本项目最大的坑**：代码按
`size = entry[11]<<16 | entry[15]<<8 | entry[19]` 拼出一个 24bit 值。
这个布局意味着：

- `entry[15]` (decomp 低 16 位的高字节) 同时充当 size 的 bits 8-15；
- `entry[19]` 恒为 `0x00` → **size 的低 8 位永远是 0**；
- 因此**任何要被游戏读取的文件，解压后大小必须是 256 的倍数**，
  否则游戏会多读/少读。原版文件全部如此对齐。

clen 字段 (16-17) 才是数据真实长度，解压器读到哪算哪；但游戏分配
缓冲区、判断搬运量用的是上述拼接值。v6 版本曾因 43956=0xABB4 未对齐
(游戏算出 0xAB00) 导致开机读字库黑屏，详见第 10 节。

SAF 内数据全部为 LZSS 压缩 (除个别未压缩的小表)，见下。

### LZSS 变体

标准 OKUMURA 变体参数：4KB 环形缓冲、初始写位置 `0xFEE`、
匹配长度 3-18、单字节 flag (LSB first)：bit=1 原始字节，bit=0 为
2 字节引用 `(T0 | (T1 & 0xF0) << 4, len = (T1 & 0xF) + 3)`。

压缩端自由度很大 (只要能解压即可)，本项目用贪婪匹配 + 512 候选链
实现 (`tools/saf.py`)，所有重建文件均通过解压往返校验。

## 3. .B 数据文件与文本结构

SAF 内的 `.B` 文件 (PACKDATA.B、STAGE01A.B、SCRIPT.B 等) 解压后为：

```
[块表] u32 块数 N + u32 × N 块偏移 (相对文件头)
[数据] 各块内容: 字符串池 / 数值表 / 指令流混合
```

字符串在池内连续排布，**单字节 `0x00` 终止**；串内 `0x7C` 是
换行控制符 (游戏渲染时换行)；部分老文本用 `0x0A`，效果相同。
SJIS 双字节 (lead 0x81-0x9F/0xE0-0xEF, trail 0x40-0xFC 排除 0x7F)、
半角 ASCII (0x20-0x7E) 与控制符混排。

文件内部寻址：文本引用用 `(块号, 块内偏移)` 或绝对偏移，由脚本解释器
按块表解析。**全部文本修改必须原位进行**——不动块表、不移动任何字符串
位置，只替换字节 + 零填充剩余空间，这是本汉化不写任何额外重定位代码的
前提。

两条特殊记录：行 442/1191 的"文本"实为图形数据误判 (假阳性)，
保留日文原文不动，工具链中以 `FP_LINES` 标记跳过。

## 4. 文本提取 (启发式判定)

从解压后的 .B 中区分"真文本"与"恰好长得像 SJIS 的图形/指令数据"
是本项目的一个主要工作量。`tools/gen_data.py` 实现的组合判据：

1. **内容判据** (命中其一即 REAL)：
   - 含假名 (`[ぁ-んァ-ヶー]`)——最强信号；
   - 含全角字母/数字/空格；
   - 含全角标点 `、。！？…―「」『』・：；（）`；
   - 纯汉字串：与"自举字典"的重合率 ≥75%/90%。
2. **自举字典**：从已知纯真文本 (STAGE01A 对话等 5 个锚点文件) 提取
   全部汉字构成字典 (553 字)，无需外部词表。
3. **结构判据** (纯汉字串辅助)：偏移 4 字节对齐 + 0x00 终止后紧跟
   ≥1 字节零填充 → 加分。
4. **孤立性过滤**：周围 160B 无其他 REAL 串的孤立 REAL，若 ≤3 字符或
   含西里尔/制表符则降级 FAKE (图形数据特征)。

粗提取共 5459 候选 (含 STAFFROL 制作名单 1994 条假名片段、TOPMENU
FACE.B 图形误报等)，精判后 1274 条 REAL 进入翻译管线。完整提取结果
(含每条原文 hex) 见 `data/original/text_extract.csv`。

> 遗漏排查经验：项目后期发现 tutorial 操作说明 9 条与任务介绍界面
> 27 条文本从未进入管线。原因有二：其一，5 个 MENU PACKDATA 中
> 0x22AF 之后是二进制数据区，其中"看起来像假名"的片段是绘图指令；
> 其二，部分文本以非 0x00 终止或长度 <4 被粗筛过滤。最终通过
> ePSXe savestate 的 RAM 搜索 (见第 11 节) 逐一定位补全 (trans_p4)。

## 5. 字库格式 KPX/TBL 与字体系统

### 文件

SYSTEM.SAF 内与字体相关的条目：

| 条目 | 说明 |
|------|------|
| `*KANJI.KPX` | 主日文字库, 16×15 px, **60B/字形**, 1024 字 (SJIS 序) |
| `KANJI.TBL`  | 主码表, 1024 项 × 2B (SJIS 双字节, LE) |
| `*KANJI2.KPX` / `KANJI2.TBL` | 副字库 (JIS 排序), 教学模式专用, 死代码陷阱见第 9 节 |

### KPX 字形布局

原版 16×15, 每行 4 字节 (x 方向 2bpp 打包)，每字形 60B：

```
pixel(x,y) = (byte[y*4 + x>>2] >> (2*(x&3))) & 3
灰度: 0=透明, 1=主笔画, 2=右下(+1,+1)偏移阴影
```

游戏按 `TBL[半角序号]` 查字形：**TBL 项值即字形在 KPX 中的顺序号**，
配合 stride 补丁 (第 6 节) 换算字节偏移。

### 自制字库

中文显示需要 1228 个简体字形，逐项决策如下：

| 维度 | 原版 | 新版 | 理由 |
|------|------|------|------|
| 字号 | 16×15 | **12×12** | 对话框 14px 行距只容 12px 高；宽度 4→3 半字 |
| 布局 | 60B/字形 (15 行×4B) | **36B/字形** (12 行×3B) | 同公式，行字节 4→3 |
| 字形来源 | — | **Windows GDI 宋体 12px 点阵** | `GetGlyphOutlineW(GGO_BITMAP)` 单色提取，自动有笔锋 |
| 阴影 | 右下偏移 | 同左 (生成时程序化补) | 保持原版视觉风格 |
| 数量 | 1024 | **1228** | 译文全部去重字符 (trans_p1-4) |

字形生成 (`reference/gen_font.py`)：GDI 提取 12px 宋体 → 基线对齐
(基线 y=10) → 居中放置 → 加右下阴影 → 2bpp 打包 36B。
GDI 提取失败的字符 (生僻符号) 生成空白字形兜底。

字符集来源：扫描全部译文 (分隔符 `|` 除外) 去重排序 →
`data/font/charset_used.txt` (1228 字)。新增译文用字必须先补字符集、
重新生成字库与码表 (见第 7 节)。

### TBL 码表

TBL 为 2B/项 LE 数组，第 i 项 = 字形 i 的 SJIS 编码。查找流程：
文本 SJIS 双字节 (lead,trail) → 在 TBL 中线性扫描匹配 → 得字形序号
→ `KPX + 序号 × stride` 取字形。**TBL 项数上限由 EXE 内 `slti`
硬编码** (原 0x400=1024，补丁改 0x4CC=1228)。

## 6. EXE 渲染代码补丁 (12 处 MIPS)

EXE 为 MIPS I 小端。装载基址 `0x80010000`，但字体相关代码段基址
`0x8000F800` (即文件偏移 = va - 0x8000F800)。12 处补丁全部围绕
"16×15→12×12" 的渲染参数修改：

| # | VA | 文件偏移 | 原指令/值 | 补丁 | 说明 |
|---|----|---------|-----------|------|------|
| 1 | 0x80030318 | 0x20B18 | `slti $v0,$v1,0x400` | `0x4CC` | TBL 查找上限 1024→1228 |
| 2 | 0x800301FC | 0x209FC | `sll $v0,$a1,4` | `sll 3` | KPX stride ×16→×8 |
| 3 | 0x80030200 | 0x20A00 | `subu $v0,$v0,$a1` | `addu` | stride ×15→×9 (即 36B/字形) |
| 4 | 0x800301F8 | 0x209F8 | `addiu $t1,$a3,0x78` | `0x48` | 字库外层循环 120→72 半字 |
| 5 | 0x80030280 | 0x20A80 | `addiu $v0,$zero,4` | `3` | VRAM 搬运宽 4→3 半字 |
| 6 | 0x80030288 | 0x20A88 | `addiu $v0,$zero,0xF` | `0xC` | VRAM 搬运高 15→12 |
| 7 | 0x80030624 | 0x20E24 | `addiu $s3,$s3,0xE` | `0xC` | 对话框全角字步进 14→12 |
| 8 | 0x80030650 | 0x20E50 | `addiu $s5,$s5,0xF` | `0xD` | 行高 15→13 |
| 9 | 0x80030744 | 0x20E9C | `addiu $s5,$s5,0xF` | `0xD` | 行高 15→13 (第二处) |
| 10 | 0x800305DC | 0x20DDC | `addiu $v1,$zero,0xF` | `0xC` | 字形精灵尺寸 15→12 |
| 11 | 0x8003069C | 0x20E9C 附近 | `addiu $s5,$s5,0xF` | `0xD` | 行高 (分支延迟槽内) |
| 12 | — | 0x65840 | `0x801FB000` | `0x801EC000` | pool[6] TBL 装载数据字 |

关键说明：

- **stride 计算** (补丁 2/3)：原 60B = 16×4 - 4；代码先 `sll 4` 再
  `subu` 得 ×15 (60B)。新 36B = 12×3：`sll 3` (×8) + `addu` (×9)
  = 36。两处必须成对修改。
- **pool[6]** (补丁 12)：字体代码从固定池指针表取 TBL 的 RAM 地址，
  原指向 `0x801FB000` (KANJI2.TBL 的装载位)，需改指主 TBL 池
  `0x801EC000`。这是"数据字"而非指令。
- 字库装载代码从 SAF 目录解析、LZSS 解压到 VRAM 上传全部复用原逻辑，
  未做任何代码注入——只要格式参数对齐，游戏自己会把新字库搬进 VRAM。

## 7. 自定义码页设计

中文文本 (1272 条) 的字符集共 1228 字，必须给每字分配一个游戏能查到
的 2 字节码。直接沿用 SJIS 排布不可行 (GBK 重码/缺字)，因此**完全
自定义码页**，但仍服从游戏的 lead/trail 合法性判定：

```
lead:  0x81-0x9F, 0xE0-0xEF      (47 个 lead × 189 个 trail)
trail: 0x40-0x7E, 0x80-0xFC      (严禁 0x7F !)
```

**0x7F 陷阱**：v7 曾将 7 个新字分配到 0x817F-0x877F (trail=0x7F)，
实测整字丢失——游戏 trail 判定 `0x40-0x7E || 0x80-0xFC`，0x7F 被
当作非法字节跳过。合法码点共 47×189=8883 个，1228 个字符从
`0x8140` 起升序分配，全部落在合法区间。

码点稳定性的重要性：码表发布后大量译文已按其编码写盘，**任何码位
变更都会使已写盘数据全部失效**。v8 新增 7 字 (─△□○伏积纸) 时，
在码表末尾追加 (0x879E-0x87A4)，前 1221 个码位一字未动。

码表三处必须一致 (`tools/verify.py` 会核对)：

1. `data/font/char_code_map.json` — 工具链编码用；
2. `data/font/KANJI.TBL` — 游戏查找用 (与 1 同序)；
3. `data/font/KANJI.KPX` — 字形按同一顺序排布。

## 8. 文本回写与空间管理

回写是本汉化唯一"侵入式"的修改，全部在 `tools/import_text.py`：

```
对每条译文:
  1. 原文校验  : 当前解压数据 [toff, toff+len) 必须等于 CSV 记录的原始 hex
                 (防错位、防重复导入错乱)
  2. 空间计算  : avail = 原文长度 + 其后连续零字节数 - 1 (保留终止符)
  3. 编码      : 自定义码页, | → 0x7C
  4. 长度检查  : len(译文编码) ≤ avail, 否则警告跳过 (不静默截断!)
  5. 写入      : 替换字节, 其后原空间清零
```

文件级流程：

```
SAF 解压 → 全部译文替换 → LZSS 重压缩 → 重压缩长度 ≤ 该文件可用空间
(本文件起始扇区 → 下一文件起始扇区) → 原位写回 + 尾部清零 → 目录 clen 更新
```

三个工程约束：

1. **不移动文件**：所有 SAF 目录扇区号保持原值，块表/字符串池偏移
   不变，游戏脚本解释器无需任何修改。
2. **不超空间**：逐文件校验重压缩长度。译文规范 (≤原文 1.2 倍、
   分段一致) 在翻译期执行，导入期是最后防线；本项目 1272 条全部
   通过，无一截断。
3. **可重入**：原文校验以 CSV hex 为准，重复导入同一镜像结果幂等。

## 9. tutorial 字体路径补丁 (KANJI2 坑)

v7 实测发现：主菜单/对话全部正常，但**教学模式 (tutorial) 界面
全部空白**。逆向定位过程 (值得同类项目借鉴)：

1. ePSXe savestate RAM 中能搜到教学文本的**自定义码页编码** →
   译文已正确进入内存，问题在渲染查询；
2. 教学文本经 SCRIPT.B 渲染 → 检查 EXE 字体池：`0x801EC000` 处
   TBL 内容被换成了 1111 项 JIS 升序表——来自 **KANJI2.TBL**；
3. 全代码搜索：游戏有**两套字体加载路径**，SCRIPT.B (教学模式)
   的加载代码硬编码字符串 `*KANJI2.KPX` / `KANJI2.TBL`，走原版
   JIS 码表 → 自定义码查不到 → 全空白。

### 修复：12 字节字符串等长替换

SCRIPT.B 解压后偏移 0x24/0x30 处的两个文件名字符串，改指主字库：

```
+0x24: '*KANJI2.KPX\0'   →  '*KANJI.KPX\0\0'      (12B, 等长)
+0x30: 'KANJI2.TBL\0\0'  →  'KANJI.TBL\0\0\0'     (12B, 等长)
```

等长替换不改变任何偏移；SCRIPT.B 重压缩后 clen 14636→14773，
仍在可用空间内。该补丁集成在 `tools/import_text.py`
(SCRIPT_B_FONT_PATCHES)，即使 SCRIPT.B 无译文条目也强制执行。

> 排查时曾怀疑 GAMEOVER/HYOUKA/ST_TITLE 等其他 overlay，逐个反编译
> 其字符串区确认它们加载的是 `*ALI.AMD` 等图形资源，与码表字体
> 无关——**全游戏只有 3 处字体加载点**：EXE 开机 (主字库)、
> SCRIPT.B (本次补丁)、TOPMENU.B (本来就指主字库)。

## 10. 踩坑实录 (黑屏/缺字/空白)

### 坑 1: 开机黑屏 (v5→v6)

**现象**：替换字库后 ePSXe 开机即黑屏，卡死。
**定位**：savestate 抓现场 → 程序死循环于读 `*KANJI.KPX` 的阻塞读。
**根因**：游戏按 `entry[11]<<16|entry[15]<<8|entry[19]` 计算解压大小
(见第 2 节)，新字库 43956=0xABB4 低字节 0xB4 ≠ 0 → 游戏算出 0xAB00，
比实际少 180B，搬运状态机等待永不出现的剩余数据。
**修复**：字库尾部补 0 对齐到 256 倍数 (补齐部分是尾部空白字形槽，
游戏不引用)。**任何替换进 SYSTEM.SAF 的文件都要做 256 对齐**。

### 坑 2: 任务介绍界面缺字 (v7→v8)

**现象**：「伏」「积」「纸」等 7 个字不显示。
**根因**：v7 追加的 7 个码位 trail=0x7F，被游戏判定非法 (见第 7 节)；
且 v7 忘记重新生成 KPX/TBL (码表加了字但字库没加)。
**修复**：码位重新分配到合法区 + 重生成字库，前 1221 码位不动。

### 坑 3: tutorial 空白 (v7→v8)

见第 9 节。根因是**多字体加载路径**，单改主字库不够。

### 坑 4: 对话行中多余空格 (v7→v8)

日文原文标点后常有全角空格表"停顿"，直译保留后中文观感差。
审计全部译文：34 处删除 (对话停顿)，128 处保留 (地图标签
「５６层　北楼梯」、武器参数「装弹数　１５发」等排版用途)。

### 经验总结

1. 换字体先弄清**全部加载路径**，不止一处；
2. 游戏自算的大小/长度字段，构造数据必须满足其**对齐约定**；
3. 码位分配永远避开非法区间 (0x7F)，且发布后冻结；
4. savestate 是定位"游戏内实际状态"的最直接证据，比静态分析快。

### ePSXe savestate 分析

savestate (`.bin`, ePSXe 1.x 已解压格式) 内含 2MB RAM (0x80000000
映射) 与 VRAM。本项目用法：

- `ss_regs.py` 系列: 解析寄存器, 定位卡死点 (PC 停在哪个循环);

- `ss_find_kana.py`: 搜索 JIS 假名编码 → 发现 KANJI2.TBL 池被换;
- RAM 地址 = 文件 0x000000 + (va - 0x80000000)。
